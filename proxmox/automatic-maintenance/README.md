# Scheduled host maintenance

The owner authorized daily automatic Proxmox host updates and reboots in the 03:00–04:00 Australia/Sydney window. The timer starts at 03:30, one hour after the configured VM backup job. This is a systemd timer rather than cron so the timezone remains explicit across daylight saving; missed runs are not caught up outside the window.

The updater takes Proxmox's `/run/vzdump.lock` non-blocking; a running backup takes priority and the run fails without changing packages. While the updater holds the lock, another backup waits or fails according to its own settings. Package indexes must refresh cleanly, the package transaction cannot remove packages, and package configuration keeps existing conffiles. It starts installation only before 03:40; an installation already in progress is not forcibly interrupted at 04:00, because that could corrupt the package database. A reboot is requested only before 03:50, after a successful package audit, when the newest version-sorted Proxmox kernel image differs from the running kernel or the standard reboot marker exists. Before reboot, each running VM must respond via its guest agent and show neither active apt timers nor a held dpkg lock. Unknown or busy guest state defers reboot. This is a point-in-time check, not a lock against a guest update starting immediately afterward.

Logs and failures: `journalctl -u proxmox-auto-update.service`; `systemctl status proxmox-auto-update.timer proxmox-auto-update.service`. Failures are recorded in the journal; no external failure notification is configured. A deferred reboot remains due on the next scheduled run if the kernel differs or the marker remains. A persistent attempt record prevents repeated reboot attempts for the same boot or a kernel that failed to boot; investigate and remove it only after resolving the problem. Stop future runs with `systemctl disable --now proxmox-auto-update.timer`. A normal apt repository upgrade may restart services and can outlast the window; it does not constitute a full host backup. Automatic major-release migrations are outside this schedule.

The recovery service is a separate, parameterized guest unit for an existing private Compose app whose port binds to Tailscale. Its root-only environment file provides site values. It runs after Docker and Tailscale, waits by retrying if the address is absent, checks the endpoint, and recreates only the affected app using the existing Compose configuration and image if needed. Do not commit the environment file. The recovery logic was checked against a healthy running service; a complete host-reboot test of the installed unit remains pending.

The scripts and units in this directory are source artifacts. Copying, enabling, or modifying them on a live host requires the operator's authorization. Before use, independently review the exact host configuration, backup behavior, package simulation, guest recovery, console access and rollback. Test the timer with `systemd-analyze calendar` and `systemd-analyze verify`; run the Python tests on Linux with `python3 test_auto_update.py`. The live system's installed version and active timer must be checked separately.
