# Focused security review — 2026-10-27

This is a point-in-time, read-only review, not a penetration test or comprehensive vulnerability scan. No configuration, packages, firewall rules, credentials or services were changed. Addresses and sensitive operational details remain in ignored site inventory. Recheck state before acting; another operator or agent may be working concurrently.

## Findings requiring review

1. **Development guest can reach infrastructure management.** A read-only TCP connection from the unprivileged `coder` account reached the Proxmox management interface and QNAP HTTPS interface. `coder` had no passwordless sudo in this check, but tools with code execution as that user have those network paths. The Proxmox firewall command reported `disabled/running`: the daemon is running, but that does not mean firewall filtering is enabled. Guest UFW reported inactive. No claim is made that those management interfaces are internet-facing. Before unattended agents or untrusted code are used, design and test explicit management isolation, including an alternate management access and rollback path. Network/firewall changes require the owner's explicit approval.
2. **Development guest release upgrade is still running or waiting.** The guest identifies itself as Ubuntu 24.04.5 while an Ubuntu release-upgrader process targeting the newer release and its temporary SSH listener are present. Ubuntu package sources point at that newer release. The upgrade process was observed sleeping, with the upgrade log not recently updated; this may be an interactive wait. The owner subsequently confirmed they started the upgrade. `dpkg --audit` returned no output at this check, which does not establish that the upgrade finished. Do not terminate it, reboot or run package upgrades until the operator confirms the active session has completed and its package state is healthy. The temporary SSH listener inherited key-only, non-root settings in the effective-config check. The simulated upgrade output for this guest cannot be treated as a normal security-update count while sources target a different release. **Status update, later on 2026-10-27:** resolved. The guest now reports Ubuntu 26.04.1 LTS with the 7.0.0-38 kernel, `dpkg --audit` is empty, no upgrades are pending, and the upgrade log shows package configuration completed before the upgrader's final "remove obsolete packages" prompt went unanswered. Package management on this guest is no longer blocked; see [shared context](../agents/context.md) for the interrupted-run details.
3. **Proxmox SSH accepts root passwords.** Effective `sshd -T` showed root login and password authentication enabled on the host. This permits password-based administrative SSH if an attacker can reach it and obtain or guess credentials; no compromise or public exposure was established. Plan a key-only administrative access change with tested access from multiple authorized devices, a working console and rollback. Host credential/SSH changes require explicit approval.
   - **Resolved 2026-10-27 at the owner's request:** installed [`proxmox/sshd/10-homelab-key-only.conf`](../proxmox/sshd/10-homelab-key-only.conf) as `/etc/ssh/sshd_config.d/10-homelab-key-only.conf` (the drop-in directory is included before the main file's `PermitRootLogin yes`, so it takes precedence). `sshd -t` passed before `systemctl reload ssh`; effective `sshd -T` shows `permitrootlogin without-password`, `passwordauthentication no`, `kbdinteractiveauthentication no`. A fresh key login succeeded, a password-only attempt returned `Permission denied (publickey)`, and the web UI on 8006 still returned HTTP 200. Authorized keys: FRAMEWORK, TITAN, `opencode@<user>` and the node's own key; only TITAN was tested from its device. The web UI and physical console still accept the root password. Rollback: delete the drop-in and reload `ssh` from the web UI shell or console.
4. **Updates need review.** A read-only `apt-get -s upgrade` using existing package indexes showed pending packages on the Proxmox host and application VM, including packages from security-labelled repositories. Cached indexes may be stale; no CVE-by-CVE assessment or repository refresh was performed. Review the applicable updates and maintenance/recovery plan separately. Do not apply updates or run package management on the development VM while its release-upgrader state is unresolved.
5. **Unexpected network listeners warrant investigation.** Proxmox and the development VM have `rpcbind` listening on all interfaces on TCP/UDP 111; the development VM also has the temporary SSH listener described above. Whether RPC is required for other infrastructure was not established. Do not disable services or alter firewall rules until dependencies are checked and the owner approves the change.

## Positive observations and limits

- The application and development guests' effective normal SSH configuration disabled password, keyboard-interactive and root SSH; `devops` was the allowed user. The temporary upgrade SSH process was checked separately.
- Paperless, its database/broker and Uptime Kuma were not privileged containers and did not mount the host Docker socket. The Paperless and Kuma published web ports were bound to the application VM's Tailscale IPv4 address. This does not verify tailnet access policy, router port forwarding, or every possible network path.
- Docker's `DOCKER-USER` chain had no additional rules at the time of inspection. Guest UFW was inactive. Docker networking can affect host firewall behavior; don't treat an inactive UFW or a running firewall daemon as proof of isolation.
- Existing published advisory pages were consulted; for example, the Paperless [filename-generation advisory](https://github.com/paperless-ngx/paperless-ngx/security/advisories/GHSA-2jhj-xqrq-rmrq) lists versions through 3.1.1 as affected and 3.1.2 as fixed; the deployed app reports 3.3.4. This single comparison is not an image vulnerability scan. [Uptime Kuma advisories](https://github.com/louislam/uptime-kuma/security/advisories) were also reviewed at a high level.
- QNAP certificate identity, MFA, router WAN exposure/forwarding, Tailscale policy, image dependency CVEs, physical NAS-loss behavior and recovery were not fully assessed. No vulnerability scanner was installed or run. QNAP backups remain deferred by the owner.

## Next steps

Confirm completion and package health of the owner-started development VM release-upgrade session first; preserve its existing state while investigating. Before running unattended coding agents or expanding services, prepare a reviewed isolation plan and a separate host SSH-hardening plan, including tests and rollback, then obtain the required approval. Review pending security updates after confirming package sources and upgrade state. Repeat this review after approved changes; do not treat this document as authorization for them.
